在配置 **Sing-box** 客户端时，开启 **TUN 模式（虚拟网卡模式）** 是实现全系统流量接管的“终极方案”。它能像 VPN 一样接管整台电脑的网卡流量，甚至无需任何系统代理环境变量，就能自动加速命令行（Terminal）、各种 IDE 依赖拉取以及大型联机游戏。

然而，对于日常编写代码、运行虚拟化容器的开发者而言，开启 TUN 模式也常常会触发各种匪夷所思的**“网络幽灵事件”**：

- 本地的 **WSL2** 虚拟机莫名连不上网，无法更新依赖；
- **Docker 容器** 启动后，拉取镜像直接超时，或者容器内部无法解析外网 DNS；
- 试图在命令行 `git clone` 某个开源库时，频繁弹出 `SSL certificate problem` 握手错误；
- 本地启动的 Web 服务或本地数据库（如连接 `localhost:3306` / `127.0.0.1`），在调试时被误导向代理出站导致连接被阻断。

今天，我们将从 TUN 模式的路由表接管机制入手，彻底为您厘清这些开发环境冲突，并给出最完美的 Sing-box 优化配置。

## 🔍 一、TUN 模式的路由接管与冲突根源

当你在 Sing-box 配置文件中开启 `auto_route` 与 `strict_route` 时，Sing-box 会在系统中创建一个名为 `singbox-tun` 的虚拟网卡，并修改系统的全局路由表：

1.  **改变默认网关的跃点（Metric）**：使所有的出站 IP 流量（包括 TCP, UDP 和 ICMP）的路由优先级全部低于 `singbox-tun` 网卡，从而迫使流量都流向 Sing-box 核心。
2.  **接管 DNS 查询**：拦截系统所有的 `53` 端口 UDP 请求，强制路由给 Sing-box 的内部 DNS 引擎进行防污染分流解析。

然而，**WSL2** 与 **Docker Bridge 模式** 本质上都是在宿主机（Windows/macOS）上创建了各自的“虚拟局域网（VLAN）和网络交换机”。由于全局路由表被强制修改，这些虚拟交换机的回源流量全部被判定为外网出站流量，强行送入了虚拟网卡，造成了**路由环路**或 **DNS 转发断连**。

## 🛠️ 二、核心解决指南：WSL2 虚拟机与 Docker 断网

### 1. 开启“局域网共享”参数

要让 WSL2 虚拟机或 Docker 容器能够借用宿主机的 Sing-box 代理，我们必须在 `inbounds` 的 `tun` 模块中声明允许局域网设备连接：

```json
"inbounds": [
  {
    "type": "tun",
    "tag": "tun-in",
    "interface_name": "singbox-tun",
    "stack": "system", // 推荐在 Windows/Mac 上使用原生 system 协议栈，兼容性更佳
    "auto_route": true,
    "strict_route": true,
    "inet4_address": "172.19.0.1/30"
  }
]
```

### 2. 豁免虚拟网段路由（关键）

我们必须告诉 Sing-box 路由引擎，当流量的目标 IP 是 WSL2 网段或 Docker 虚拟网卡网段时，**必须直接放行（direct），不要走代理出站**。

在配置文件的 `route.rules` 中，加入以下网段豁免规则：

```json
{
  "route": {
    "rules": [
      {
        "ip_cidr": [
          "127.0.0.0/8", // 本地回环 IPv4
          "172.16.0.0/12", // Docker 默认网段 & 局域网 B 类
          "192.168.0.0/16", // 局域网 C 类 & 很多 WSL 默认分配网段
          "10.0.0.0/8", // 局域网 A 类
          "169.254.0.0/16" // 链路本地地址 (Link-local)
        ],
        "outbound": "direct"
      }
    ]
  }
}
```

> [!TIP]
> **WSL2 终极解决方案（镜像模式）**：
> 如果你使用的是 Windows 11 较新版本，建议不要使用默认的 NAT 网卡。在 Windows 用户目录 `C:\Users\<你的用户名>\` 下新建或编辑 `.wslconfig` 文件，写入以下配置：
>
> ```ini
> [wsl2]
> networkingMode=mirrored
> ```
>
> 保存后在 cmd 执行 `wsl --shutdown` 重启。镜像模式会让 WSL2 与 Windows 共享完全相同的物理网卡和回环接口，这能从根本上避免 TUN 网卡冲突，让 WSL2 天然获得完美代理。

## 🔒 三、解决本地 Localhost / 127.0.0.1 阻断

很多开发者在本地开发网页或连接本地 MySQL、Redis 时，经常会报连接超时。这是因为开启 `strict_route` 后，原本发往 `127.0.0.1` 的请求被 TUN 接管了，并送给了 `final` 规则对应的代理服务器。

为了保证本地端口通信畅通无阻，必须在 Sing-box 配置文件中的 `route` 模块启用**本地回路豁免**，确保 `localhost` 和局域网主机直接访问：

```json
{
  "route": {
    "rules": [
      {
        "domain": ["localhost"],
        "outbound": "direct"
      },
      {
        "domain_suffix": [".local"],
        "outbound": "direct"
      }
    ]
  }
}
```

此外，还要特别注意避坑：不要随意开启 `dns.fakeip` 作为全局默认解析模式，或者将 `localhost` 加入 FakeIP 解析池中。这会导致本地 IP 被劫持为 `28.0.0.x` 的虚拟 FakeIP，导致浏览器和 IDE 握手彻底失败。

## 🌐 四、解决 Git SSL 证书报错

在开启代理后，很多极客使用 `git clone` 或 `git push` 时常遇到类似如下的错误：
`fatal: unable to access 'https://github.com/xxx': SSL certificate problem: unable to get local issuer certificate`

### 根源分析

这通常是由于你的代理软件开启了 **HTTP 代理**（且没有将证书导入系统可信根证书中），或者是开启 TUN 模式后，Git 使用的 `libcurl` 库与 TUN 虚拟网卡之间的 TLS 协商产生了证书链冲突。

### 优雅修复策略

不要直接关闭 SSL 安全校验（那会让你面临严重的安全扫描风险）。请在 Git 命令行中针对 GitHub 单独配置代理通道：

```bash
# 全局针对 Github 走 SOCKS5 代理（推荐，假定你本地 Sing-box 的 inbound socks 监听 7890 端口）
git config --global http.https://github.com.proxy socks5://127.0.0.1:7890

# 若你想让所有 git 流量统一走 SOCKS5 代理
git config --global http.proxy socks5://127.0.0.1:7890
```

如果您想撤销此配置，可随时运行：

```bash
git config --global --unset http.proxy
git config --global --unset http.https://github.com.proxy
```
