## 🧩 一、配置文件的骨架：五大模块

Sing-box 的 `config.json` 看似复杂，其实只有五个顶级模块，数据按固定顺序流转：

```
流量进入 → inbounds → route → outbounds → 发往公网
              ↓           ↑
             dns（解析）   rule_set（规则库）
```

| 模块 | 职责 | 一句话理解 |
| :--- | :--- | :--- |
| `inbounds` | 流量入口 | TUN 虚拟网卡 / SOCKS5 / HTTP 入站，把系统流量"接进来" |
| `dns` | 解析管道 | 独立的 DNS 路由，决定每个域名"找谁问 IP" |
| `route` | 交通调度 | 按规则决定每个连接走代理还是直连 |
| `outbounds` | 流量出口 | 你的节点、直连、拦截，流量的"目的地" |
| `rule_set` | 规则库 | 二进制 .srs 文件，route 和 dns 引用的"地图" |

记住这个顺序，后面所有配置都是在这五个格子里填空。**第一次读建议通读，第二遍对照自己的配置文件逐段改。**

## 🔌 二、inbounds：把流量接进来

最常用的是 **TUN 入站** —— 创建一张虚拟网卡接管全系统流量：

```json
{
  "type": "tun",
  "tag": "tun-in",
  "interface_name": "singbox-tun",
  "inet4_address": "172.19.0.1/30",
  "auto_route": true,
  "strict_route": true,
  "stack": "system",
  "sniff": true
}
```

- `auto_route` + `strict_route`：自动接管系统路由，TUN 模式的灵魂；
- `sniff: true`：**FakeIP 模式下必须开** —— 从 TLS 握手中嗅探真实域名，否则域名分流规则全部失效；
- `stack: system`：用系统协议栈，兼容性最好。

TUN 与 Docker/WSL2 冲突的调优见 [《Sing-box TUN 模式终极调优》](/posts/singbox-tun-mode-wsl2-docker-optimization/)。

## 🌐 三、outbounds：流量的出口与策略组

出站分两类：**真实节点**（vless/hysteria2/trojan…）和**策略组**（selector/urltest）。

### 策略组：节点的"遥控器"

```json
{
  "type": "selector",
  "tag": "proxy",
  "outbounds": ["auto-fallback", "node-us-reality", "node-hk-hys2", "direct"],
  "default": "auto-fallback"
},
{
  "type": "urltest",
  "tag": "auto-fallback",
  "outbounds": ["node-us-reality", "node-hk-hys2"],
  "url": "https://www.gstatic.com/generate_204",
  "interval": "3m",
  "tolerance": 50
}
```

- `selector`：手动选择的"总开关"，客户端界面上点选的就是它；
- `urltest`：每 3 分钟自动测速，自动选延迟最低的节点，`tolerance: 50` 表示延迟差距 50ms 内不切换（防抖）。

节点群组管理的完整玩法见 [《Sing-box 节点群组管理：URLTest 自动测速与选择器模式》](/posts/sing-box-urltest-selector-groups/)。

### 真实节点示例（VLESS-Reality）

```json
{
  "type": "vless",
  "tag": "node-us-reality",
  "server": "us.yourdomain.com",
  "server_port": 443,
  "uuid": "your-uuid-here",
  "flow": "xtls-rprx-vision",
  "tls": {
    "enabled": true,
    "server_name": "www.microsoft.com",
    "utls": { "enabled": true, "fingerprint": "chrome" },
    "reality": {
      "enabled": true,
      "public_key": "YOUR_REALITY_PUBKEY",
      "short_id": "YOUR_SHORT_ID"
    }
  }
}
```

2026 年记住两个铁律：`flow` 用 `xtls-rprx-vision`，uTLS 指纹用 `chrome`。Reality 的 SNI 筛选与防探测见 [《Reality 防封锁黑魔法》](/posts/sing-box-vless-reality-sni-guide/)。

## 🚦 四、route：交通调度中心

`route.rules` **自上而下匹配、命中即止** —— 顺序就是一切。推荐的通用顺序：

1. **DNS 劫持**：`protocol: dns → dns-out`，先把 DNS 流量收进管道；
2. **局域网放行**：`127.0.0.0/8`、`192.168.0.0/16` 等 → `direct`；
3. **广告拦截**：`geosite-ads → block`；
4. **国内直连**：`geosite-cn` + `geoip-cn → direct`；
5. **兜底**：`final: proxy`，其余全部走代理。

想用逻辑组合（"既是 BT 流量**又是**非国内 IP 才直连"）？Sing-box 支持 `and`/`or` 逻辑规则，详解见 [《Sing-box 路由规则配置进阶》](/posts/sing-box-routing-advanced/)。

## 🎯 六、5 个真实场景的 route 写法

模板是起点，真实需求长这样（加在 `route.rules` 数组里，注意顺序）：

**场景 1：ChatGPT / Claude 强制走美国专线**
```json
{ "rule_set": ["geosite-openai"], "outbound": "node-us-reality" }
```
（需自建 openai 规则集，见 [《自定义规则集编译教程》](/posts/sing-box-srs-ruleset-compilation/)）

**场景 2：BT / P2P 下载直连，不占代理带宽**
```json
{ "rule_set": ["geosite-bittorrent"], "outbound": "direct" }
```

**场景 3：公司内网域名直连**
```json
{ "domain_suffix": ["corp.example.com"], "outbound": "direct" }
```

**场景 4：指定 App 走指定节点（需 sniff）**
```json
{ "process_name": ["Telegram.exe"], "outbound": "node-hk-hys2" }
```

**场景 5：流媒体解锁走解锁专用节点**
```json
{ "rule_set": ["geosite-netflix"], "outbound": "node-us-reality" }
```
流媒体分流策略见 [《Apple TV 原生 Sing-box 分流实战》](/posts/apple-tv-singbox-tvos-setup-guide/)。

## 🔧 七、排错：配置报错的三板斧

1. **先过 JSON 校验**：90% 的启动失败是少逗号/多逗号，把配置贴到 `jsonlint.com` 先验证；
2. **开 debug 日志**：把 `log.level` 改成 `debug`，重启看第一条报错，它会精确告诉你哪个字段非法；
3. **二分法注释**：一次注释掉一半模块，能启动就说明问题在另一半，快速定位。

抓包与日志分析的完整方法见 [《Sing-box 抓包与排错指南》](/posts/singbox-clash-api-web-panel-troubleshooting-dns-leak/)。

## 🖥️ 八、服务端视角：客户端配置对应的服务端长什么样？

理解客户端配置后，很多人好奇：服务端的 `config.json` 是什么结构？其实是镜像对称的 —— 客户端的 `outbounds` 对应服务端的 `inbounds`：

```json
{
  "inbounds": [
    {
      "type": "vless",
      "tag": "vless-in",
      "listen": "::",
      "listen_port": 443,
      "users": [
        { "uuid": "your-uuid-here", "flow": "xtls-rprx-vision" }
      ],
      "tls": {
        "enabled": true,
        "server_name": "www.microsoft.com",
        "reality": {
          "enabled": true,
          "handshake": { "server": "www.microsoft.com", "server_port": 443 },
          "private_key": "YOUR_REALITY_PRIVATE_KEY",
          "short_id": ["YOUR_SHORT_ID"]
        }
      }
    }
  ]
}
```

关键对应关系：客户端 `outbounds` 里的 `uuid` / `flow` / `reality.public_key`，必须和服务端 `inbounds` 里的 `users[].uuid` / `flow` / `reality.private_key` 配对。任何一边写错，握手直接失败 —— 这也是排错时先对一遍两端参数的原因。

完整的服务端从零部署教程见本站第三总纲 [《VPS 主机从零部署 Sing-box 节点服务端实战》](/posts/vps-singbox-vless-reality/)。


## 🗂️ 十一、配置文件的模块化拆分：告别 500 行大 JSON

配置膨胀到几百行后，单文件维护是灾难。Sing-box 支持用多文件拆分（需 1.11+，待实测你所用版本的支持情况）：

```
config/
├── config.json        # 主文件：只留 inbounds + include
├── dns.json           # DNS 模块
├── route.json         # 路由规则
├── outbounds.json     # 出站与策略组
└── rule_set.json      # 规则集定义
```

思路：按本文"五大模块"一模块一文件，改路由只动 `route.json`。配合 Git 版本管理（第九节），回滚粒度精确到模块。

## 📋 十二、常用字段速查表

| 字段 | 位置 | 作用 | 2026 推荐值 |
| :--- | :--- | :--- | :--- |
| `sniff` | inbounds.tun | 嗅探真实域名 | `true`（FakeIP 必开） |
| `flow` | outbounds.vless | 流控模式 | `xtls-rprx-vision` |
| `fingerprint` | tls.utls | TLS 指纹伪装 | `chrome` |
| `detour` | dns.servers | DNS 查询走哪条出站 | 国外 `proxy` / 国内 `direct` |
| `final` | dns / route | 兜底 | `dns-proxy` / `proxy` |
| `strategy` | dns | 解析策略 | `ipv4_only`（防 IPv6 绕行） |
| `download_detour` | rule_set | 规则集走哪下载 | `proxy` |
| `tolerance` | urltest | 测速防抖阈值 | `50` |

## ❓ 常见问题与 AI 快问快答 (FAQ)

### Q1: 在 FakeIP 模式下为什么必须开启 `sniff: true` 流量嗅探？

**答**：FakeIP 下数据包目标 IP 是假 IP（如 `198.18.x.x`）。开启 `sniff` 能从 TLS 握手中嗅探出真实域名，`route.rules` 的域名分流才能生效。

### Q2: 生产环境下自建节点配合商业机场的最佳实践是什么？

**答**：`selector` 里主节点用自建 **CN2 GIA** / **AS9929** 专线 VPS，商业机场作 `auto-fallback` 备用池，隐私与容灾兼得。评测见 [《"饿饭CC云"深度评测》](/posts/efan-cc-cloud-review/)。

### Q3: `final: proxy` 和 `final: direct` 该怎么选？

**答**：科学上网场景选 `proxy`（默认走代理，国内规则直连）；纯隐私场景有人选 `direct` 兜底（默认直连，只代理命中规则的）。新手用 `proxy` 最省心。

### Q4: 规则集多久更新一次？

**答**：远程 `.srs` 建议每天自动更新一次，见 [《Rule Set 配置与自动更新全攻略》](/posts/sing-box-rule-set-ultimate-guide/)；也可以用 cron 脚本，见 [《Bash 脚本定时更新规则》](/posts/sing-box-auto-update-rules/)。

### Q5: 手机端和桌面端能共用一套配置吗？

**答**：核心结构通用，但 inbounds 建议分开：手机用 `tun` 入站即可，桌面端可按需加 SOCKS5 入站给特定软件用。分应用代理见 [《移动端分应用代理教程》](/posts/sing-box-mobile-clients/)。

### Q6: Mux（多路复用）应该开吗？

**答**：Mux 把多个请求复用到一条 TCP 连接上，能显著降低弱网下的握手延迟，但会增加单连接被限速的风险。建议：手机流量、浏览网页开 Mux；大文件下载、看 4K 视频关 Mux 走直连复用。深度解析见 [《深度揭秘 Sing-box 的 Mux 优化》](/posts/sing-box-mux-multiplexing/)。

### Q7: 配置里能写注释吗？JSON 不是不支持注释？

**答**：标准 JSON 确实不支持注释，但 Sing-box 使用了带注释扩展的 JSONC 解析 —— 配置文件里可以直接写 `//` 单行注释，本文模板里的注释就是这么来的。放心用，但别把注释写进通过 API 下发的订阅里（某些精简客户端可能不兼容）。

## 🚀 十、进阶：Mux 多路复用与连接复用

出站支持 `multiplex` 字段开启 Mux：

```json
{
  "type": "vless",
  "tag": "node-us-reality",
  "server": "us.yourdomain.com",
  "server_port": 443,
  "uuid": "your-uuid-here",
  "flow": "xtls-rprx-vision",
  "multiplex": {
    "enabled": true,
    "protocol": "h2mux",
    "max_connections": 4,
    "min_streams": 4
  },
  "tls": { "enabled": true }
}
```

- `protocol: h2mux`：基于 HTTP/2 的多路复用，兼容性最好；
- `max_connections: 4`：最多维持 4 条底层连接，超过就复用；
- 适用：高延迟 VPS（美西/欧洲）+ 碎片化请求（刷信息流、API 调用）；
- 不适用：Reality + `xtls-rprx-vision` 已自带流控优化，叠加 Mux 收益递减，大流量场景建议关闭。
