很多手搓 VPS 自建 Sing-box 节点的朋友，常会遭遇突然的重击：**VPS IP 被 TCP 阻断（被墙）了**。

海外工具检测服务器在线，但国内终端连线直接超时。遇到这种情况，最经典的零成本解法就是 —— **套用免费的 Cloudflare CDN 边缘代理**。

今天我们将通过 Sing-box 服务端配合 **WebSocket (WS)** 与高性能 **gRPC** 协议套上小黄云，让“被墙小鸡”起死回生！

> [!NOTE]
> **📌 核心速览（TL;DR / 快问快答）：**
>
> - **CDN 复活原理**：客户端与 Cloudflare 边缘节点建立 HTTPS 握手，CF 在云端将流量回源分发给被墙的 VPS，真实 IP 被隐藏在云后。
> - **协议限制**：Cloudflare 仅支持代理 HTTP/HTTPS 类流量，必须使用 **VLESS + WebSocket** 或 **VLESS + gRPC**（严禁配置 `flow: "xtls-r-flow"`）。
> - **延迟与提速**：默认分配的 CDN IP 晚高峰可能拥堵，配合 **CloudflareST（优选 IP 工具）** 将 `server` 改为本地低延迟 IP 可达到秒开 4K。

## 🛠️ 1. Sing-box 服务端配置 (WebSocket / gRPC 双入站)

在 VPS 上的 `/etc/sing-box/config.json` 部署回源入站：

```json
{
  "inbounds": [
    {
      "type": "vless",
      "tag": "vless-ws-in",
      "listen": "::",
      "listen_port": 80,
      "users": [
        {
          "uuid": "your-client-uuid",
          "flow": ""
        }
      ],
      "transport": {
        "type": "ws",
        "path": "/mysecret-ws",
        "max_early_data": 2048,
        "early_data_header_name": "Sec-WebSocket-Protocol"
      }
    },
    {
      "type": "vless",
      "tag": "vless-grpc-in",
      "listen": "::",
      "listen_port": 8080,
      "users": [
        {
          "uuid": "your-client-uuid",
          "flow": ""
        }
      ],
      "transport": {
        "type": "grpc",
        "service_name": "mysecret-grpc"
      }
    }
  ],
  "outbounds": [
    {
      "type": "direct",
      "tag": "direct"
    }
  ]
}
```

## 📱 2. Sing-box 客户端出站配置 (支持优选 IP)

```json
{
  "type": "vless",
  "tag": "vless-cf-grpc",
  "server": "104.16.88.88", // 填入通过 CloudflareST 优选出的极速 IP
  "server_port": 443,
  "uuid": "your-client-uuid",
  "tls": {
    "enabled": true,
    "server_name": "cdn.yourdomain.com",
    "insecure": false
  },
  "transport": {
    "type": "grpc",
    "service_name": "mysecret-grpc"
  }
}
```

## 🌩️ Cloudflare 域名侧的正确姿势

VPS 端配好只是半边，Cloudflare 侧三处必查：

1. **DNS 小黄云必须点亮**（Proxied）：灰云等于直连，CDN 没生效。
2. **SSL/TLS 加密模式选 Full (strict)**：VPS 回源是 80/8080 明文？那选 Flexible 也行，但 Full 更安全。回源配了 TLS 就必须 Full (strict)。
3. **端口白名单**：CF 只代理特定端口（80、443、2053、2083、2087、2096、8443 等），回源端口必须在其中，`listen_port: 80` 就是这个原因。

## ⚖️ gRPC vs WebSocket：选哪个？

| | WebSocket | gRPC |
|---|---|---|
| 兼容性 | 最好，处处能过 | 少数老旧中间设备会拦截 |
| 多路复用 | 依赖配置 | 原生多路，延迟更稳 |
| 特征 | 有 WS 握手特征 | 流量特征更像正常 gRPC 调用 |

**建议**：优先 gRPC，不通再切 WS。两个入站可以共存（像本文配置一样），客户端哪个通就用哪个。

## 🚀 优选 IP 的正确用法

CloudflareST 扫出延迟最低的 CF 边缘 IP 后：

1. 客户端 `server` 填优选 IP（如 `104.16.88.88`）。
2. **`tls.server_name` 必须填真实域名**（`cdn.yourdomain.com`），这是 SNI，CF 靠它找到你的域名。
3. 优选 IP 会变，每 1-2 周重扫一次，或者写个定时脚本。

注意：优选 IP 是"就近接入 CF 边缘"，回源到 VPS 的那段路程省不了，跨国延迟下限摆在那。

## ⚠️ 风险提示：Cloudflare 的服务条款

社区长期有讨论：CF 官方 ToS 对"大量非 HTML 流量"有限制，免费套餐跑大流量代理**有被警告/封号的案例流传**。实测派不编造——建议：

- 别在 CF 后面跑 BT、4K 全天挂机这种流量大户。
- 重要节点准备直连备用方案，CF 只当"复活甲"。
- 真要大流量，考虑付费套餐或换直连 VPS。

## 🎯 什么时候该用这招，什么时候不该？

**该用**：IP 被墙、预算为零、轻度使用（网页、聊天、轻量视频）。
**不该用**：打游戏（延迟 180ms+ 起步）、大流量下载、需要稳定商用的场景——这时候直连 CN2 GIA VPS 或商业专线才是正解。

### Q1: 套用 Cloudflare CDN 之后打游戏延迟高怎么解决？

**答**：由于流量经过跨国 CDN 边缘折返，物理延迟会在 180ms - 300ms 左右。游戏与实时语音建议切换到基于 **中国电信 CN2 GIA** 或 **联通 AS9929** 的直连 VPS，或使用商业 IPLC 专线。

### Q2: 为什么改用优选 IP 后提示握手失败？

**答**：使用优选 IP 时，必须确保 `tls.server_name` 依然填写为你托管在 CF 上的真实域名（如 `cdn.yourdomain.com`），否则 CDN 边缘节点无法定位路由。

### Q3: 套了 CDN 之后，VPS 原来的直连端口还能用吗？

**答**：能。CDN 只是多了一条"前门"，VPS 的 443 端口本身还在。建议直连和 CDN 双配置都保留，CF 抽风时切回直连应急。

### Q4: gRPC 的 service_name 有什么讲究？

**答**：相当于路径密码，服务端和客户端必须一致。用随机字符串（如 `x7f9k2`），别用 `proxy`、`grpc` 这种一眼假的名字。
