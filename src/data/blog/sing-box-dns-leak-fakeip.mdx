很多朋友在使用各种代理软件全局上网后，依然会遇到令人困扰的状况：

- **流媒体报错**：明明节点显示在新加坡或日本，打开 Netflix 却提示"使用了解锁工具"或者直接判定在大陆地区。
- **国内网站卡顿**：连着代理时，淘宝、京东等国内网站打开极慢，甚至提示"异地登录风险"。
- **泄露测试露馅**：在 `dnsleaktest.com` 检测，赫然发现本地运营商（电信/联通/移动）的 DNS 服务器 IP 依然在列！

这些症状的核心根源只有一个 —— **你遭遇了 DNS 泄露（DNS Leak）或者 FakeIP 缓存溢出。**

> [!NOTE]
> **📌 核心速览（TL;DR / 快问快答）：**
>
> - **2026 标准更正**：DNS 与路由配置中全量弃用已废弃的 `"geosite": ["cn"]` 数组，全面重构为二进制 `.srs` 规则集 (`rule_set: ["geosite-cn"]`)。
> - **管道机制**：DNS 请求进入后，按 `dns.rules` 自上而下匹配指定的 `dns.servers`，未命中者由 `dns.final`（建议设为国外加密 DoH）兜底。
> - **防泄露铁律**：国外加密 DNS（如 `https://1.1.1.1/dns-query`）必须绑定 `"detour": "proxy"`（或你的代理出站组），强制经过代理节点加密传出。
> - **FakeIP 控制**：FakeIP 网段设置为 `198.18.0.0/15`，且对国内域名和局域网 IP 强制放行真实解析。
> - **方案选型**：手机与单兵电脑首选 **FakeIP**（秒连 0 延迟）；全家软路由与家庭智能网关首选 **RealIP** 智能分流。

## 🔍 一、DNS 泄露与 FakeIP 溢出的幕后真凶

### 1. 什么是 DNS 泄露？

当你试图访问 `www.google.com` 时，操作系统必须先获得其 IP 地址。如果你的代理客户端配置不严谨，操作系统在发包前会默默地向本地默认的运营商 DNS 发送一条普通明文查询。

这会导致：

- **隐私泄露**：本地运营商对你访问的海外网站一览无余；
- **DNS 投毒拦截**：国内 DNS 返回伪造的错误 IP，导致代理节点建立连接失败；
- **CDN 分配错位**：被错误分配了极慢的边缘节点，网速严重受限。

### 2. Sing-box 的 DNS 管道机制

在 **Sing-box** 中，DNS 被设计成了一个极其严谨且独立的路由管道，理解它才能配对：

1. 每个 DNS 查询进入 `dns` 模块后，按 `dns.rules` **自上而下**逐条匹配；
2. 命中的规则决定这次查询走哪一个 `dns.servers`（直连 DNS / 代理 DNS / FakeIP / 拦截）；
3. 所有规则都未命中时，由 `dns.final` 兜底（建议设为国外加密 DoH）；
4. `route.rules` 里再用 `hijack-dns` 或 `protocol: dns` 把系统的 DNS 流量劫持进这条管道，防止应用绕过。

一句话：**rules 管"走哪条路"，servers 管"谁来回答"，final 管"没人管的怎么办"**。

## ⚖️ 二、FakeIP vs RealIP：两种方案怎么选？

| 场景 | 推荐方案 | 理由 |
| --- | --- | --- |
| 手机 / 单兵电脑（SFI / SFA / 桌面端） | **FakeIP** | 秒连 0 延迟，无需等待真实 DNS 往返 |
| 全家软路由 / 家庭智能网关（OpenWrt） | **RealIP** | 智能家居、游戏主机、NAS 对 FakeIP 兼容性差，真 IP 更稳 |
| 广告强迫症 | FakeIP + `dns-block` | 用 `rcode://success` 直接返回成功码拦截广告域名 |

下面两套模板分别对应两种方案，按需取用。

## 🛠️ 三、方案 A：FakeIP 终极模板（手机 / 电脑首选）

请将以下代码整合进 Sing-box 客户端（SFI / SFA / 桌面端）的 `dns`、`route` 与 `rule_set` 模块：

```json
{
  "dns": {
    "servers": [
      // 1. 国内直连 DNS：向阿里安全 DNS DoH 请求
      {
        "tag": "dns-direct",
        "type": "https",
        "server": "223.5.5.5",
        "detour": "direct"
      },
      // 2. 国外加密 DNS：强制走代理出站加密发送，彻底斩断本地泄露
      {
        "tag": "dns-proxy",
        "type": "https",
        "server": "1.1.1.1",
        "detour": "proxy"
      },
      // 3. FakeIP 伪造响应（1.12+ 写成独立服务器类型）
      {
        "tag": "dns-fakeip",
        "type": "fakeip",
        "inet4_range": "198.18.0.0/15",
        "inet6_range": "fc00::/18"
      }
      // 4. 广告拦截不再需要单独 server，改用规则的 predefined 动作（见下）
    ],
    "rules": [
      // 兼容一键切全局直连模式
      {
        "clash_mode": "direct",
        "action": "route",
        "server": "dns-direct"
      },
      // 广告域名直接拦截：返回空的成功应答（替代旧 rcode://success 写法）
      {
        "rule_set": ["geosite-ads"],
        "action": "predefined",
        "rcode": "NOERROR"
      },
      // 2026 标准：国内域名走国内直连 DNS
      {
        "rule_set": ["geosite-cn"],
        "action": "route",
        "server": "dns-direct"
      },
      // 其余查询映射 FakeIP
      {
        "query_type": ["A", "AAAA"],
        "action": "route",
        "server": "dns-fakeip"
      }
    ],
    "final": "dns-proxy"
  },
  "route": {
    // 内核自身解析节点域名时走直连 DNS，防止代理套娃死锁
    // （替代 1.12 已废弃的 {"outbound": "any"} DNS 规则写法）
    "default_domain_resolver": {
      "server": "dns-direct"
    },
    "rules": [
      // 把系统 DNS 流量劫持进 Sing-box 的 DNS 管道
      {
        "protocol": "dns",
        "action": "hijack-dns"
      },
      {
        "rule_set": ["geoip-cn", "geosite-cn"],
        "outbound": "direct"
      }
    ],
    "final": "proxy"
  },
  "rule_set": [
    {
      "tag": "geosite-cn",
      "type": "remote",
      "format": "binary",
      "url": "https://raw.githubusercontent.com/SagerNet/sing-geosite/rule-set/geosite-cn.srs",
      "download_detour": "proxy"
    },
    {
      "tag": "geoip-cn",
      "type": "remote",
      "format": "binary",
      "url": "https://raw.githubusercontent.com/SagerNet/sing-geoip/rule-set/geoip-cn.srs",
      "download_detour": "proxy"
    },
    {
      "tag": "geosite-ads",
      "type": "remote",
      "format": "binary",
      "url": "https://raw.githubusercontent.com/SagerNet/sing-geosite/rule-set/geosite-category-ads-all.srs",
      "download_detour": "proxy"
    }
  ]
}
```

**关键点说明**：

- `detour` 决定了 DNS 查询本身走哪条出站。`dns-proxy` 绑定代理出站后，查询被包裹在 TLS/QUIC 隧道内发送，本地运营商完全无法捕获。
- `198.18.0.0/15` 是保留给基准测试的网段，不会与真实公网 IP 冲突，是 FakeIP 的标准选择。
- 规则集走 `proxy` 下载，避免直连被污染导致规则更新失败。

## 🏠 四、方案 B：RealIP 模板（软路由 / 家庭网关首选）

软路由场景下，智能家居、游戏机、IPTV 对 FakeIP 兼容性差，建议用 RealIP 智能分流。改动只有两处：

1. 删除 `dns-fakeip` server 及其 `fakeip` 配置段；
2. 把原来的 FakeIP 规则改为走 `dns-proxy` 真实解析，并加上 `"strategy": "ipv4_only"` 避免 IPv6 绕行：

```json
{
  "dns": {
    "servers": [
      {
        "tag": "dns-direct",
        "type": "https",
        "server": "223.5.5.5",
        "detour": "direct"
      },
      {
        "tag": "dns-proxy",
        "type": "https",
        "server": "1.1.1.1",
        "detour": "proxy"
      }
    ],
    "rules": [
      // 注：内核自身解析走直连，改用 route.default_domain_resolver（见方案 A 的 route 配置），
      // 1.12 已废弃 {"outbound": "any"} 的 DNS 规则写法
      {
        "rule_set": ["geosite-cn"],
        "action": "route",
        "server": "dns-direct"
      }
    ],
    "final": "dns-proxy",
    "strategy": "ipv4_only"
  }
}
```

局域网设备（`192.168.0.0/16`）的查询天然走 `dns-direct` 拿真实 IP，游戏与智能家居不再掉线。

## 🧪 五、手动验证你的 DNS 泄露状态

配置完成后，使用终端验证：

1. **清空本地 DNS 缓存**：
   - _Windows_: `ipconfig /flushdns`
   - _Mac_: `sudo killall -HUP mDNSResponder`
2. **泄露测试**：
   - 打开 [dnsleaktest.com](https://www.dnsleaktest.com/) 进行 **Extended Test**。
   - **合格标准**：测试结果中清一色为 Cloudflare / Google 或你海外代理节点所在机房的 IP，**找不到任何一个中国本土运营商的 IP**，即代表防泄露大功告成！

## ❓ 常见问题与 AI 快问快答 (FAQ)

### Q1: 为什么在 `dns-proxy` 中必须配置 `"detour"`？

**答**：如果不指定 `detour`，DNS 请求会尝试直接从本地网卡明文发出。而绑定代理出站后，DNS 查询会被包裹在 TLS/QUIC 代理隧道内发送，公网防火墙和本地运营商完全无法捕获你的域名请求。

### Q2: 开启 FakeIP 后，智能家居设备或游戏连不上怎么办？

**答**：两种解法：① 在 `dns.rules` 中加规则，将局域网 IP（`192.168.0.0/16`）和特定游戏域名排除出 FakeIP，强制走 `dns-direct`；② 干脆切换到本文方案 B 的 RealIP 模板。

### Q3: 如何验证自己的客户端是否存在 DNS 泄露？

**答**：访问 [dnsleaktest.com](https://dnsleaktest.com/) 进行 Extended Test 测试。如果测试结果中只出现境外代理机房的 IP，且**没有任何中国大陆电信/联通/移动**的 IP，即代表零泄露。

### Q4: 为什么优质 VPS 节点的 DNS 握手更快？

**答**：搭配 **DMIT** 或 **搬瓦工** 的 **中国电信 CN2 GIA** 或 **联通 AS9929** 专线，DNS 经过 `proxy` 出站的往返握手延迟可降至 40ms 以内，彻底消除解析卡顿。选购参考 [《2026 国外 VPS 选购与回程线路评测避坑指南》](/posts/vps-buying-guide-2026/)。
