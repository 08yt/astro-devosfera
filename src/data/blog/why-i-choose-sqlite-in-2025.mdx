过去很长一段时间，在严肃的技术社区讨论 Web 生产环境数据库时，如果提及 **SQLite**，常常会招致鄙夷：“那不是客户端 App 或浏览器本地存缓存的玩具吗？”

只要启动一个稍微正规的项目，开发者往往会本能地 `docker compose up -d mysql postgresql`，并欣然接受后台常驻吃掉几百兆乃至上 GB 的系统内存。

然而到了 2026 年，随着 NVMe 固态硬盘吞吐爆发、WAL（预写式日志）机制成熟以及 Litestream / Cloudflare D1 等边缘生态的兴起，**SQLite 正以恐怖的读性能与近乎为零的运维心智负担，成为中小型服务与全栈开发者的绝对主力！**

> [!NOTE]
> **📌 核心速览（TL;DR / 快问快答）：**
>
> - **微秒级无网络延迟**：作为嵌入式 C 函数库直接运行在进程内，彻底省去 TCP 握手与本地 Unix Socket 序列化开销，单次读取延迟低于 10 微秒（比 MySQL/Postgres 快数倍）。
> - **WAL 预写日志读写并发**：开启 `PRAGMA journal_mode = WAL;` 后，写操作仅追加 WAL 文件，读写完全互不阻塞，读并发性能极高。
> - **零运维单文件基石**：整个数据库仅为一个 `.db` 磁盘文件，备份只需直接复制，迁移只需打包文件，常驻内存开销为 0MB。
> - **Litestream 实时异地灾备**：配合 Litestream 自动监听 WAL 增量，毫秒级将数据块流式同步至 Cloudflare R2 / S3，彻底打破“单机无法高可用”的偏见。

## ⚙️ 生产级 SQLite 必须开启的四大 PRAGMA 调优

若要在 Web 后端（如 Node.js、Go、Python 或 Rust）中发挥 SQLite 的极限性能，在建立连接时务必执行：

```sql
-- 1. 开启 WAL 模式 (读写互不阻塞，核心基石)
PRAGMA journal_mode = WAL;

-- 2. 设置同步级别为 NORMAL (在 WAL 下兼具数据安全与数倍写入速度)
PRAGMA synchronous = NORMAL;

-- 3. 强制启用外键级联约束
PRAGMA foreign_keys = ON;

-- 4. 调整缓存大小为 64MB 内存 (负数表示 KB)
PRAGMA cache_size = -64000;

-- 5. 延长写锁等待超时时间至 5000 毫秒 (避免 busy timeout 报错)
PRAGMA busy_timeout = 5000;
```

## 🚀 配合 Litestream 实现毫秒级云端异地容灾

单文件最怕“机器硬件物理损坏”？在服务启动时附带一个轻量的 **Litestream** 后台任务：

```yaml
# /etc/litestream.yml
dbs:
  - path: /opt/app/data.db
    replicas:
      - type: s3
        bucket: homelab-sqlite-backup
        path: db
        endpoint: https://<account_id>.r2.cloudflarestorage.com
        access-key-id: ${R2_ACCESS_KEY}
        secret-access-key: ${R2_SECRET_KEY}
```

每当应用写入一行数据，Litestream 在几十毫秒内自动将增量 WAL 帧上传至 Cloudflare R2，实现接近于零的恢复点目标（RPO）！
